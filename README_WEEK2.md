What Classes Will I Create?
Instead of throwing everything into one giant class and hoping for the best, I decided to split the project into four classes. Each one has its own job and stays in its lane.
•	Calculator.java: This is the main class and the one that runs when you hit play. It does not do much on its own honestly. It creates the Scanner, waves hello to the other classes, and gets everything started. Think of it as the manager who delegates everything and then takes all the credit.
o	Inside Calculator.java
	main(): This is the function that runs first when the program starts. It creates the Scanner, calls Menu to show the startup screen, and kicks off the main loop. Everything else branches off from here. It is basically the opening scene of the movie.

•	Menu.java: This class handles everything the user sees that is not math. The banner, the random quote, the welcome message, the help table, and the goodbye message all live here. It also reads what the user types and figures out where to send them. It is basically the front desk of the whole operation. 
o	Inside Menu.java
	printHeader(): Prints the opening banner with the project title, week number, and my name. Runs once at the very start. No parameters, no return value, just vibes and println statements.
	printWelcome(): Prints the welcome message and basic instructions. Also grabs a random quote to display on startup. No parameters and does not return anything.
	getRandomQuote(): Picks a random quote from a list and returns it as a String. Using String array to hold all the quotes and a Random object to pick one. The cryptic zombie quote that hints at the easter egg lives in this list. 
	printHelpMenu(): Prints the full command reference table. Right at the very bottom, all alone, is ...zombie? with no description and no explanation. Just sitting there. Waiting. No parameters and does not return anything.
	printClosing(): Prints the goodbye message when the user exits. Short, sweet, and slightly dramatic. No parameters and does not return anything.
	handleInput(): This is the main input loop. It sits and waits for the user to type something, figures out what it is, and sends it to the right place. Math goes to Commands, ZOMBIE goes to Zombies, HELP prints the table, EXIT says goodbye. Nonsense goes to checkEasterEgg which is where things get interesting. Takes a Scanner as a parameter and does not return anything.
	checkEasterEgg(): Keeps track of how many times in a row the user has typed complete garbage. First time gets a normal error. Second time gets a slightly more annoying response. Third time the program gives up entirely, reveals the ZOMBIE command, and throws them straight into Apocalypse mode as punishment for their chaos. No mercy. Takes the invalid input as a parameter and does not return anything.

•	Commands.java: This is where all the real work happens. Every math operation and every memory function live here. It also handles all the error checking so if someone tries to divide by zero or types their name instead of a number this class catches it before anything explodes. The engine room. Nobody sees it but nothing works without it.
o	Inside Commands.java
	addition(): Asks for two whole numbers, adds them, and prints the result in the format 6 + 5 = 11. Takes a Scanner as a parameter and does not return anything.
	subtraction(): Asks for two decimal numbers, subtracts them, and prints the formatted result with trailing zeros trimmed. Takes a Scanner as a parameter and does not return anything.
	multiplication(): Asks for two numbers, multiplies them, and prints the result. Takes a Scanner as a parameter and does not return anything.
	division(): Asks for two numbers and divides them. Checks if the second number is zero first because we are absolutely not letting the universe collapse on our watch. Takes a Scanner as a parameter and does not return anything.
	modulus(): Asks for two numbers and returns the remainder after division. The most misunderstood operation in math. Takes a Scanner as a parameter and does not return anything.
	multiValueOperation(): Handles SUM, AVG, MIN, and MAX. The user types a keyword followed by a bunch of numbers and this function figures out what they want, does the math across all the values, and prints the result. Takes a Scanner as a parameter and does not return anything.
	displayResult():Handles all result formatting for the entire program. Takes the two values, the operator, and the result as parameters and prints it in the standard style. One function for all formatting means if the style ever needs to change it only has to be fixed in one spot instead of hunting it down across the whole project.
	memoryStore(): Saves the last result into the memory slot. Takes the value as a double parameter and does not return anything. Print confirmation so the user knows it works.
	memoryRecall(): Returns whatever is sitting in memory so it can be used in a new calculation. Take no parameters and return a double. If memory is empty, it lets the user know instead of just returning zero and causing confusion.
	memoryClear(): Wipes memory clean and confirms it. No parameters and does not return anything. Very satisfying to use.
	memoryPeek(): Shows what is in memory without touching it. No parameters and does not return anything. Just a quick look.
	handleError(): Handles all error messages across the calculator. Take the error type as a String and print the right friendly message. Keeping all errors in one function means the tone stays consistent and nobody gets a boring generic error message.

•	Zombies.java: This class runs the entire Zombie Gauntlet game from start to finish. Once it takes over it handles everything until the game ends and then hands control back to the calculator. Think of it as a restaurant inside a hotel. Same building but its own whole thing going on inside.
o	Inside Zombies.java
	startZombieGauntlet(): The entry point for the game. Shows the mode selection screen, checks which modes are unlocked, and launches whatever the player picks. Takes a Scanner as a parameter and does not return anything.
	playZombieMode(): Runs the actual game loop. Tracks lives, manages doors, handles right and wrong answers, triggers the spooky atmosphere descriptions, activates the countdown timer after the second wrong answer, and shows the win or lose screen when it is all over. Takes a Scanner, the number of doors, and the difficulty level as parameters and does not return anything.
	generateQuestion(): Creates a random math problem based on difficulty. Easy doors get simple addition and subtraction. Middle doors get multiplication and division. Final doors throw decimals, large numbers, and modulus at the player just to make sure they really want that freedom. Takes a difficulty integer as a parameter and returns the question as a String and the answer as a double.
	displayLives(): Prints the current lives as hearts on the screen so the player always knows exactly how close to becoming zombie food. Takes lives remaining as a parameter and does not return anything.
	displayWin(): Shows the escape scene when the player clears all the doors. Prints total time, mistake count, and a verdict that judges their performance. Then unlocks the next mode and asks if they want to go again. It takes time, mistakes, and mode as parameters and does not return anything.
	displayGameOver(): Shows the game over screen when the player loses all three lives. Dramatic. Probably has sound effects in my head even though it is a console app. Takes doors survived and mode as parameters and does not return anything.
	unlockNextMode(): Checks which mode was just beaten and unlocks the next one in line. Survivor unlocks Escapee, Escapee unlocks Gauntlet, Gauntlet unlocks Apocalypse. Takes the completed mode as a parameter and does not return anything.

How Will the Program Flow Logically?
When the program starts Calculator.java fires up first. It creates the Scanner and immediately hands things off to Menu.java which prints the banner, grabs a random quote, and shows the welcome message. After that Menu just sits in the input loop like a very patient receptionist waiting for the user to do something. Everything the user types goes through handleInput in Menu.java first. It reads the input and decides where it needs to go. Math expressions and memory commands go to Commands.java. HELP prints the table right there. ZOMBIE hands control over to Zombies.java. EXIT checks if anything is in memory, warns the user if so, prints the goodbye, and closes everything down. Complete gibberish goes to checkEasterEgg which tracks the chaos and eventually punishes the user accordingly. Any time Commands.java finishes a calculation it sends everything to displayResult which formats it and prints it in the standard style. Any time something goes wrong handleError steps in with a friendly message, so nothing crashes and nobody feels bad about it. For the Zombie Gauntlet the flow is its own self-contained loop inside Zombies.java. It shows the mode screen, the player picks a mode, and playZombieMode takes over completely. It generates a question, waits for an answer, and either moves forward or drops a life depending on whether the player actually paid attention in math class. After the second wrong answer the timer kicks in because apparently pressure was needed. Lose all three lives and displayGameOver runs. Clear all the doors and displayWin runs, the next mode unlocks, and the player gets to decide if they want to go again or return to being a normal calculator user. The whole thing keeps looping back to the main input prompt in Menu.java until the user types EXIT. That is the only civilized way out. Zombies offer a much less civilized alternative.
